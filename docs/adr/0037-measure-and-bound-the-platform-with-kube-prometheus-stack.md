# 0037. Measure and bound the platform: metrics, alerts and explicit resource limits

- **Status:** Accepted
- **Date:** 2026-09-26

## Context

[ADR 0015](0015-use-kube-prometheus-stack-for-observability.md) chose kube-prometheus-stack.
Installing it raises questions the ADR left open: how much the platform may consume on a
single development host, how long metrics are kept, where alerts go, and which component
owns the monitors for components that are installed before the monitoring CRDs exist.
Memory is the scarcest resource: when it runs out, the kernel kills processes, typically the
largest ones (etcd, the API server).

## Options

| Concern | Option | Trade-off |
|---|---|---|
| Resource budget | Profile-gated components (heavy ones only in `perf`) | `dev` does not show the full platform |
| | **Explicit requests and limits everywhere, one replica, measure after each addition; gate by profile only if needed** | Tuning effort; limits must be revisited as load grows |
| Retention | Time only / size only | Unbounded disk, or unpredictable history |
| | **Both; whichever is reached first (`dev`: 3 days / 2 GiB)** | Short history in `dev` (disposable anyway) |
| Alert delivery | Paging channel now | Credentials and routing before they are needed |
| | **UI only (null receiver); a channel later** | Alerts are seen only when looked at |
| Monitors for bootstrap components | In their own charts | Chart install fails before the CRDs exist |
| | **Owned by the monitoring component (PodMonitors/ServiceMonitors)** | Monitor definitions live away from the component |

## Decision

- Every workload in the monitoring stack declares requests and limits; memory limits are set,
  CPU limits are not (to avoid throttling), CPU requests are.
- Prometheus retention: 10 days / 8 GiB by default, 3 days / 2 GiB in `dev`.
- Alertmanager routes to a null receiver. First platform alerts are symptom-based with a
  runbook link: Argo CD application out of sync (30 min) or unhealthy (15 min), certificate
  renewal failing (under 14 days left), certificate not ready.
- Cilium and Argo CD expose metrics endpoints only; their monitors are defined in
  `gitops/platform/monitoring`. Automated components (cert-manager) own their monitors.
- On kind, etcd, scheduler, controller-manager and kube-proxy targets are disabled
  (`values-substrate-kind.yaml`): they listen on the node's loopback and would only raise
  false alerts.
- The Grafana admin password is generated by OpenTofu and provided by the bootstrap stack.

## Consequences

- Measured after installation: lab memory about 5 GB, with a few GB still available to the
  node VM; Kyverno, secrets management and logging must be measured the same way.
- Found during rollout: pod limits protect nodes, not the host. With no cap on the node
  containers, the simultaneous restart of monitoring, Cilium and Argo CD saturated every CPU
  available to Docker and made the host unresponsive; node containers are now CPU-capped
  ([0034](0034-run-the-lab-as-a-guest-on-its-host.md)).
- Also found: Grafana needs a startup probe (the liveness probe killed it during its first
  start) and a memory limit sized from measurement (256Mi caused reclaim thrashing); manual
  syncs must pass the Application's sync options, otherwise large dashboards fail the
  client-side `last-applied` annotation limit.
- Metric cardinality is a design constraint for the services in Phase 4: no unbounded label
  values (order or account IDs) in metrics.
