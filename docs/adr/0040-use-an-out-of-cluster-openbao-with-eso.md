# 0040. Keep secrets in an out-of-cluster OpenBao, delivered by External Secrets Operator

- **Status:** Accepted
- **Date:** 2026-10-07

## Context

Until now the only application secret (the Grafana admin login) was generated by the
bootstrap stack and written as a Kubernetes Secret. Phase 3 adds Kafka users, schema-registry
and service credentials. We need one place for secret values that survives cluster rebuilds
(clusters are disposable, [0034](0034-run-the-lab-as-a-guest-on-its-host.md)), no secret
material in Git, no new hand-held secret besides secret zero
([0026](0026-keep-a-single-secret-zero-in-the-os-keychain.md)), and a pattern that maps to an
enterprise setup.

## Options

| Option | Pros | Cons |
|---|---|---|
| **OpenBao outside the clusters + External Secrets Operator** | Secrets outlive clusters; Git holds references only; Vault-compatible API; one store for all profiles | One more lab container; one more trust relationship per cluster |
| OpenBao inside each cluster + ESO | Closest to a production deployment | Secrets die with the cluster; unseal on every start; more memory in `dev` |
| SOPS + age, encrypted in Git | No server, almost no memory | Argo CD needs a plugin; manual rotation; no dynamic secrets or PKI later |
| Sealed Secrets | Small controller | Key bound to the cluster: every rebuild needs re-sealing |

Licenses: OpenBao MPL-2.0 (Linux Foundation), External Secrets Operator Apache-2.0, the
`hashicorp/vault` OpenTofu provider MPL-2.0. HashiCorp Vault itself (BUSL) is not used.

## Decision

- **Store:** OpenBao 2.7 (pinned by digest) as container `kfep-openbao`, like the state store:
  no auto-start, data in a bind mount outside the repository, port 8200 on loopback only. It
  joins the `kind` Docker network so pods and API servers reach it by name. TLS with a server
  certificate from the lab root ([0035](0035-terminate-tls-at-a-single-gateway-with-a-lab-pki.md)).
- **No new human secret:** a static seal key (32 random bytes) auto-unseals it, and the
  declarative `initialize` stanza creates an admin login on the first start; its root token
  is revoked after use. Key and login exist only in encrypted state and in the container.
  The audit log goes to stdout and is declared in the configuration (this version rejects
  audit devices enabled during self-initialization).
- **Three layers, three stacks:**

  | Stack | Owns | Lifetime |
  |---|---|---|
  | `secrets-store` | Container, seal key, admin login | Host (all profiles) |
  | `secrets` | KV v2 mount per profile, read policy, generated values | Independent of clusters |
  | `bootstrap` | Kubernetes auth mount and role for this cluster | Per cluster |

- **Delivery:** External Secrets Operator is an addon
  ([0039](0039-keep-dev-light-with-core-and-addon-components.md)). One `ClusterSecretStore`
  per cluster can read only its profile's mount. It logs in with a dedicated service account;
  OpenBao checks that token with a TokenReview made with the same token
  (`system:auth-delegator`), so no long-lived reviewer token exists.
- The Grafana admin login is the first secret moved: an `ExternalSecret` in the monitoring
  component, which now `requires: [external-secrets]`.

## Consequences

- A cluster rebuild keeps every secret value; only the Kubernetes auth mount is recreated.
- Secret zero now also protects the OpenBao seal key: `lab:backup` archives OpenBao's data
  with the state, and the archive is useless without secret zero.
- Every OpenTofu run of `bootstrap` needs OpenBao running (`lab:start` starts it).
- The store runs on the Mac host and serves the kind substrate only. A Proxmox cluster needs
  OpenBao on its own network; the substrate contract already exposes the internal API address.
- With the addon disabled (`dev` default) nothing delivers secrets; the monitoring addon
  cannot be enabled without it.
- Known limits: a single node without HA; the static seal is weaker than an HSM or cloud
  KMS (acceptable for a lab whose trust anchor is the OS keychain); dynamic database and PKI
  secrets are not used yet.
